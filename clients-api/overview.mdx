## This surface is retired

The `/api/v1` client-management routes still exist, but they are **internal to
Mythic operators** and require a staff credential. They were published here as
though they were part of the product, which they never were, and that mistake
had consequences: an integration authenticating with the old static admin key
broke when that key was retired, with no deprecation window, because nothing
recorded who was calling.

Everything an agency needs is on `/client/v1`, behind the agency key (`ak_`)
you already hold.

## Why the replacements are not identical

Two differences will show up immediately if you are porting a caller.

**The client id is server-generated.** `POST /client/v1/locations` rejects
`id`, `agency_id`, and `plan_id` rather than accepting them — the first because
a caller-chosen id lets one agency squat another's id namespace, the second
because it is what enforces tenant isolation, the third because it is a billing
decision. Store the id the response returns.

**Scoping is a parameter, not a path segment.** `/client/v1` routes name the
client with `?location_id=` or the `X-Location-Id` header, and a location that
is not linked to your agency is refused. See
[Authentication](/get-started/authentication).

<Callout kind="note">
  Agency and location *administration* — creating agencies, linking locations
  to them — has no agency-scoped form, because an agency key is scoped to one
  agency. Those routes remain staff-only under
  [Agencies (staff)](/agencies-api/overview).
</Callout>
