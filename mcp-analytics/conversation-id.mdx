## How a session is chosen

A session groups the calls of one agent conversation. The SDK picks the first of these that exists:

1. The `conversation_id` argument, when `enableConversationId` is on.
2. The session id set by the [session middleware](#the-session-header).
3. The transport's own session id (stdio, or a Streamable HTTP server that keeps sessions).
4. `sessionKey(ctx)` from your code, combined with the client name and version, with a 30-minute idle window.
5. One session per client, kept in memory, with a 30-minute idle window. On a server built per request, the key is the client name and version plus, when the request is authenticated, a hash of the principal.

The principal is a user id your auth layer puts in `authInfo.extra` (`sub`, `userId`, `user_id` or `principal`), else `authInfo.token`, else the `Authorization` or `X-API-Key` header. Only a hash is used, never the credential. `authInfo.clientId` alone is not a principal: it names the OAuth client app, which many users share. So one client app never merges different users on a hosted server, and one key never merges different client apps.

The stored `session_id` is `mcps_` followed by 32 hex characters, a hash of the server name and the raw id. When the transport has its own session id, a hash of it is also kept as `mcp_session_id`: `mcpsid_` followed by 16 hex characters. Mythic never stores the raw transport id.

Session state lives in the shared client, not in the server object, so a server built for every request still keeps one session per conversation. The client keeps at most 10,000 sessions.

## Which one you need

| Server | Sessions come from | What to add |
| --- | --- | --- |
| stdio | The process: one client per process | Nothing |
| Streamable HTTP that keeps sessions (`Mcp-Session-Id`) | The transport | Nothing |
| Streamable HTTP without sessions, 2025 protocol | The session middleware | `mythicSessionNode` or `mythicSessionFetch` |
| Stateless, a server per request (for example `createMcpHandler`), or any 2026-07-28 request | Client app and authenticated principal, with a 30-minute idle window | Nothing. `sessionKey(ctx)` or `enableConversationId` for finer sessions |

**Sessions look fragmented** (one call per session) when none of these applies. Add `sessionKey` or `enableConversationId`. An unauthenticated stateless server groups every user of one client app into one session: add `sessionKey` there.

## The session header

`@mythic-data/mcp/http` sets an `Mcp-Session-Id` header for 2025-protocol servers that do not set one. Protocol 2026-07-28 has no `initialize` and no `Mcp-Session-Id`, so the middleware does nothing for it:

```ts
import { mythicSessionNode, mythicSessionFetch } from '@mythic-data/mcp/http';

// Express and other (req, res, next) servers
// Mount after a JSON body parser so it can see initialize.
app.use('/mcp', express.json(), mythicSessionNode({ sessionSecret: process.env.MYTHIC_SESSION_SECRET }));

// Fetch-style handlers
export default { fetch: mythicSessionFetch(handler, { sessionSecret: env.MYTHIC_SESSION_SECRET }) };
```

- On an `initialize` request with no `Mcp-Session-Id`, it creates a token and sets the header on the response, for JSON and SSE replies.
- On later requests that send the header back, it makes that session available to `instrument`.
- A header the transport sets itself always wins.

The token is `mys1.<id>.<issued>.<signature>` with `sessionSecret`, or `mys0.<id>.<issued>` without. It is valid 24 hours. Once a `sessionSecret` is set, unsigned `mys0` tokens are ignored. On Cloudflare Workers the `/http` entry needs the `nodejs_compat` flag.

<Callout kind="alert">
The session token is an analytics hint. Never use it for authorization.
</Callout>

It works with clients that send `Mcp-Session-Id` back on every request. It does nothing for stdio, or for stateless clients that never send it back: use `sessionKey` or `enableConversationId` there.

## sessionKey

```ts
instrument(server, {
  client: mythic, // from createMythicClient({ apiKey, host })
  sessionKey: (ctx) => ctx.headers?.['x-user-id'],
});
```

Return a value that is stable for one caller. Calls with the same key, from the same client app (name and version), with no gap over 30 minutes, form one session.

<Callout kind="info">
From SDK 3.110, sessions on servers without a transport session id are split by client app and by authenticated principal. Before 3.110, a `sessionKey` grouped every client app on that key into one session, and stateless servers grouped every user of one client app. Session and anonymous-user counts go up after the upgrade, and sessions recorded before it do not continue.
</Callout>

## conversation_id

With `enableConversationId: true`, the SDK adds an optional `conversation_id` string (kept up to 200 characters) to every tool's schema and removes it before your handler runs, as it does for [`context`](/mcp-analytics/intent#the-context-argument). An agent that sends the same value on every call keeps its calls in one session across reconnects and servers. A tool that defines its own `conversation_id` is left alone.

It is off by default because it adds a field to every tool and depends on the agent filling it in. `metadataOnly` turns it off.
