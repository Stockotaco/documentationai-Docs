## Entry points

| --- | --- |
| `@mythic-data/mcp` | `instrument`, `createMythicClient`, `MythicMCP` |
| `@mythic-data/mcp/http` | `mythicSessionNode`, `mythicSessionFetch` |

The package is ESM with no runtime dependencies and needs Node.js 18 or later.

## instrument(server, options)

```ts
const mythic = createMythicClient({ apiKey: 'pk_…', host: 'https://mythic-analytics.gulp.workers.dev' });
const handle = instrument(server, { client: mythic, ...options });
// handle: { capture, flush, shutdown, observed, unobserved, mythic, client }
```

`server` is an `McpServer` or a low-level `Server` from `@modelcontextprotocol/server` 2.x or `@modelcontextprotocol/sdk` 1.22.0 to 1.32.2 (the tested range; older 1.x releases are not verified). The SDK finds the low-level server (`server.server` on an `McpServer`) and wraps its request handlers for `initialize`, `tools/list`, `tools/call` and `resources/read`, including handlers set later.

For a paginated `tools/list`, `instrument` reads at most 20 pages, with a 2-second deadline for SDK-initiated discovery through your own list handler. This deadline does not include the host page the client requested. Discovery runs on a first page with more pages (to find host tool names), and on a server built per request that gets a `tools/call` or a cursor-page `tools/list` before any first-page `tools/list` (to index the tools). A fresh stateless cursor-page response keeps its schemas unchanged unless this bounded discovery establishes completeness.

Discovery only runs when the SDK edits `tools/list` (`context`, `conversation_id` or `get_more_tools` on). With `metadataOnly`, or with all three off, it never reads your list handler: calls pass through untouched. Cursors are opaque: any `cursor`, including an empty string, is a later page, and discovery follows a `nextCursor` of `""`. Only an absent `nextCursor` ends the list.

If discovery is incomplete because of the page cap, deadline, cursor cycle, invalid page or handler failure, the SDK injects no fields or virtual tool and does not intercept calls as virtual `get_more_tools` calls. Host calls pass through unchanged until a complete first-page discovery.

`observed` lists the methods the SDK wraps and grows as handlers are registered. `unobserved` lists methods registered before `instrument` that it could not reach. Calling `instrument` before registering tools avoids this. `instrument` never throws: given an object that is not an MCP server, or no `apiKey` or `client`, it logs a warning and returns a handle that observes nothing.

### Options

| Option | Default | Meaning |
| --- | --- | --- |
| `client` | | A client from `createMythicClient`. One per process, shared by every server instance. |
| `apiKey` | | Shortcut: a publishable key (`pk_…`) that creates a client with default settings when `client` is not given. Prefer `client`. |
| `context` | `true` | Add the optional `context` argument to every tool. See [Intent](/mcp-analytics/intent). |
| `intentFallback(call)` | | `({ toolName, arguments, info }) => string`. An intent for a call that has no `context`, stored with `intent_source: 'fallback'`. |
| `reportMissing` | `true` | Add the `get_more_tools` tool. See [Missing capabilities](/mcp-analytics/missing-capability). |
| `missingCapabilityToolName` | `'get_more_tools'` | Name of that tool. |
| `enableConversationId` | `false` | Add an optional `conversation_id` argument to every tool and use it as the session. See [Conversation ID and sessions](/mcp-analytics/conversation-id). |
| `captureParameters` | `true` | `boolean`, a list of top-level argument names to keep, or `(toolName) => boolean \| string[]`. |
| `captureResponses` | `true` | Same forms, for the tool result. |
| `captureErrorMessages` | `true` | Keep the error text of failed calls (at most 1 KB). |
| `captureExceptions` | `true` | Send an error thrown by a handler (not a protocol error) as a Mythic `$exception` too. |
| `metadataOnly` | `false` | Turns off parameters, responses, intent and the `context` argument, error messages, `get_more_tools`, `conversation_id`, exceptions and `$set`. `tools/list` is unchanged. |
| `redact` | `{ pii: true }` | `{ pii: false }` stops redacting emails, phone numbers, card numbers and US SSNs. Key, value and URL redaction cannot be turned off. |
| `limits` | `{ depth: 10, breadth: 100, string: 8192, eventBytes: 32768 }` | Caps applied to every event. `string` is in characters. `eventBytes` is clamped to 60 KB, so an event always fits the server's 64 KB limit. |
| `identify(ctx)` | | Returns `{ distinctId, properties? }`, or a promise of it. `null`, `undefined` or a throw keeps the call anonymous. See [Identifying users](/mcp-analytics/identifying-users). |
| `sessionKey(ctx)` | | Returns a stable key for the caller when the transport has no session. The SDK combines it with the client name and version. |
| `eventProperties(ctx)` | | Extra properties merged into every event before redaction. |
| `toolCategory(name)` | | Returns a category for a tool (at most 100 characters), stored as `tool_category`. |
| `beforeSend(event)` | | Edit an event, or return `null` to drop it. A throw drops it too. Runs after redaction, and the result is redacted and truncated again. |
| `enabled` | `true` | `false` sends nothing and changes nothing. |

`ctx` is the SDK's view of one request, the same in both MCP SDK versions. See [Stateless requests](#stateless-requests-protocol-2026-07-28) for where `client` and `protocolVersion` come from. Fields: `method`, `toolName`, `arguments` (with injected fields removed), `transportSessionId`, `headers` (lowercased), `authInfo`, `client` and `server` (`{ name, version }`), `protocolVersion`, `transport`, `conversationId`, `model`, and `raw`, the host SDK's own request context.

### The handle

| Member | Meaning |
| --- | --- |
| `capture(event)` | Queue a custom event through the shared client. |
| `flush()` | Send what is queued now. |
| `shutdown(timeoutMs)` | Flush with a deadline and stop the shared client. |
| `observed` | The methods being recorded. |
| `unobserved` | Methods registered before `instrument` that could not be observed. |
| `mythic` | The `MythicMCP` core, for hosts that also call it directly. |
| `client` | The shared client. |

## The client

```ts
import { createMythicClient } from '@mythic-data/mcp';

const client = createMythicClient({ apiKey: 'pk_…', host: 'https://mythic-analytics.gulp.workers.dev' });
```

| Option | Default | Meaning |
| --- | --- | --- |
| `apiKey` | | Publishable key. Required. |
| `host` | `https://mythic-analytics.gulp.workers.dev` | Ingestion host. |
| `flushAt` | `20` | Send when a queue holds this many events. |
| `flushInterval` | `5000` | Send at least this often, in milliseconds. Not used when `waitUntil` is set. |
| `maxQueue` | `1000` | Events kept in memory per queue. Past this, new events are dropped and counted. |
| `fetch` | global `fetch` | Custom fetch. |
| `waitUntil` | | `(promise) => void`, for serverless runtimes. |
| `logger` | `console` | `{ warn, debug? }`, where the SDK reports its own problems. |
| `sessionSecret` | | Signs session tokens. See [Conversation ID and sessions](/mcp-analytics/conversation-id#the-session-header). |
| `retry` | `{ maxRetries: 2, maxDelayMs: 30000 }` | Retries for 429, 5xx and network failures. |

Use **one client per process** and pass it to every server instance. A server built per request (for example with `createMcpHandler`) shares the client's session state and its single timer. MCP events and standard events (`$exception`, `$set`) are sent in separate batches of at most 100 events and 900 KB.

| Method | Meaning |
| --- | --- |
| `capture(event)` | Queue an event. |
| `flush()` | Send what is queued. |
| `shutdown(timeoutMs)` | Flush with a deadline and stop. |
| `stats()` | `{ sent, dropped, droppedByReason, rejected, rejectedByReason, queued, pausedUntil, timers }`. |

## Servers without an SDK server object

A server with its own JSON-RPC dispatcher uses `MythicMCP` and calls it from the dispatcher. It takes the same options as `instrument` and applies the same schema injection, redaction and caps. The constructor throws a `TypeError` when neither `apiKey` nor `client` is given.

```ts
import { MythicMCP } from '@mythic-data/mcp';

const mythic = new MythicMCP({ client }); // client from createMythicClient({ apiKey, host })

// tools/list: answer with the prepared list
const tools = mythic.prepareToolList(myTools);
mythic.captureToolsList(info, myTools.map((t) => t.name));

// tools/call
const call = mythic.prepareToolCall(name, rawArgs);
if (call.isMissingCapability) {
  mythic.captureMissingCapability(info, rawArgs);
  return mythic.missingCapabilityReply();
}
const startedAt = Date.now();
try {
  const result = await runTool(name, call.arguments); // injected fields removed
  mythic.captureToolCall(info, call, { result, startedAt, durationMs: Date.now() - startedAt });
  return result;
} catch (error) {
  mythic.captureToolCall(info, call, { error, startedAt, durationMs: Date.now() - startedAt });
  throw error;
}
```

`info` is the request description `instrument` builds for you (`ctx` above). Fill in what your dispatcher knows: at least `method`, and `server`, `client` and `transportSessionId` when you have them.

| Method | Records |
| --- | --- |
| `prepareToolList(tools, { firstPage?, hostToolNames?, discoveryComplete? })` | Nothing. Returns the list with `context`, `conversation_id` when enabled, and `get_more_tools` on the first page. Pass `firstPage: false` for later pages. With a paginated list, pass the later pages' tool names as `hostToolNames` on the first page, so a host tool named `get_more_tools` on a later page suppresses the virtual one. Pass `discoveryComplete: false` if discovery is capped or fails. This disables field and virtual-tool injection and virtual interception until a complete first-page discovery. |
| `prepareToolCall(name, args)` | Nothing. Returns `{ toolName, arguments, intent, intentSource, conversationId, isMissingCapability }`, with the injected fields removed from `arguments`. |
| `missingCapabilityReply()` | Nothing. The fixed result to return for `get_more_tools`. |
| `captureInitialize(info)` | `$mcp_initialize` |
| `captureToolsList(info, toolNames)` | `$mcp_tools_list` |
| `captureToolCall(info, call, { result?, error?, startedAt?, durationMs? })` | `$mcp_tool_call`, and `$exception` for a thrown error |
| `captureResourceRead(info, { uri, isError, startedAt?, durationMs? })` | `$mcp_resource_read` |
| `captureMissingCapability(info, args)` | `$mcp_missing_capability` |

## Stateless requests (protocol 2026-07-28)

MCP protocol revision 2026-07-28 has no `initialize` handshake and no `Mcp-Session-Id`. Each request names its client and protocol version in `_meta`. A server built per request (for example with `createMcpHandler`) is observed the same way as any other.

| Field | Read from, first match wins |
| --- | --- |
| Client name and version | The request's `_meta` `io.modelcontextprotocol/clientInfo`, else this server instance's `initialize`, else the low-level server's recorded client |
| Protocol version | The request's `_meta` `io.modelcontextprotocol/protocolVersion`, else this instance's `initialize` result, else the server's negotiated version, else the `mcp-protocol-version` request header |

The header fallback covers 2025-era HTTP clients on a server built per request, where the instance that answered `initialize` is gone by the next call. Client capabilities are not recorded.

Sessions on such servers are split by client app and by authenticated principal. See [Conversation ID and sessions](/mcp-analytics/conversation-id).

## HTTP session middleware

The middleware only matters for the 2025 protocol, on Streamable HTTP servers that do not issue their own `Mcp-Session-Id`. It acts on `initialize`, so it does nothing for stdio or for 2026-07-28 requests.

| Function | For |
| --- | --- |
| `mythicSessionNode(opts)` | Node-style `(req, res, next)` servers such as Express |
| `mythicSessionFetch(handler, opts)` | Fetch-style `(req: Request) => Promise<Response>` handlers |

Options: `sessionSecret` (else the client's), `client`, `now`, and for Node `isInitialize(req)` when no parsed `req.body` is available. On Cloudflare Workers the `/http` entry needs the `nodejs_compat` flag, because it uses `node:async_hooks`.

See [Conversation ID and sessions](/mcp-analytics/conversation-id#the-session-header).

## Changes in 3.110

| Version | Change |
| --- | --- |
| 3.110.0 | Sessions on servers without a transport session id are split by client app (name and version) and, when the request is authenticated, by a hash of the principal. `sessionKey(ctx)` is combined with the client name and version. Session and anonymous-user counts go up after the upgrade, and sessions recorded before it do not continue. |
| 3.110.0 | With nothing injected into `tools/list` (`metadataOnly`, or `context`, `conversation_id` and `get_more_tools` all off), a server built per request no longer runs tool discovery. |
| 3.110.0 | An empty-string cursor is a valid cursor: it is a later page, and discovery follows it. |
| 3.110.0 | The protocol version falls back to the `mcp-protocol-version` request header. |
| 3.110.0, 3.110.1 | The `/calls` and `/sessions` lists return `protocol_version`. See the [API reference](/mcp-analytics/api). |
